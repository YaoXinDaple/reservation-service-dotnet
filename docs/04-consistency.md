# 冗余表、一致性与并发

本项目把一笔预订写进两张表，所以学习重点不止是调用 `ExecuteAsync`，还包括修改失败、主键变化和并发时会发生什么。

## 成功操作维护哪些数据

创建时向两张表各写一行。删除时先从确认号表取得完整业务字段，再删除确认号行与酒店日期行。更新时同样先读旧值，比较酒店日期表的完整主键是否变化。

| 修改内容 | 确认号表 | 酒店日期表 |
| --- | --- | --- |
| 客人或离店日 | 更新现有行 | 更新现有行 |
| 酒店、入住日、房号 | 更新现有行 | 删除旧主键行，写入新主键行 |

每个操作只包含两到三条相关修改，放入一个 LOGGED BATCH。Repository 不会把大量预订打成一个跨分区批次来提高导入速度。

## LOGGED BATCH 的边界

LOGGED BATCH 通过 batchlog 帮助一组修改在失败恢复时最终全部应用。它没有为这两张表提供类似关系数据库事务的跨分区隔离。

因此，客户端在批次执行或恢复期间分别读取两张表，可能观察到暂时不同步。把“读旧记录，再写入新记录”拆成读取和 BATCH，也不会自动把整个过程变成串行化事务。[Apache CQL BATCH 文档](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html#batch)

本项目的测试验证正常运行下写入成功后的结果，以及单 API 实例内并发修改的结果。它没有通过节点故障注入验证 batchlog 恢复，也没有把单节点实验当作多节点故障证明。

## 为什么有进程内 SemaphoreSlim

假设两个修改都先读到预订位于酒店 A。第一个准备把它移到 B，第二个准备移到 C。两次写入如果并发执行，都只删除 A，就可能同时留下 B 和 C 的查询记录。

Repository 使用一个单例 `SemaphoreSlim` 串行执行本实例的创建、修改、删除，让后一个修改在前一个操作结束后再读取旧值。教学项目选择一个全局门闩，便于跟读和验证；它会限制写入吞吐量。

读取没有进入这个门闩，仍可能在批次执行时观察到变化。门闩只对当前进程有效，不能协调多个 API 进程，也不能取消数据库已经接收的写入。

特别是写入超时后，批次仍可能在服务器端完成或恢复。本地门闩释放后发生的新修改，不能据此获得分布式事务保证。生产实现需要另外设计单写入者、版本化更新、可靠事件投影、幂等与对账等机制，并结合业务选择方案。

## LOCAL_QUORUM 在单节点中意味着什么

默认使用 `NetworkTopologyStrategy`，本地数据中心副本数 RF=1，读写一致性为 `LOCAL_QUORUM`。此时本地多数派就是一个副本。

这适合练习驱动配置，但停止唯一节点后数据库就不可用。把一致性级别写成 QUORUM，并不会自动产生副本；RF 与节点拓扑必须一起配置。

本项目没有提供三节点 Compose。后续如果增加多节点，应分别验证数据中心名称、RF、节点状态和读写级别，再做停节点实验。

## LWT 为什么只放在实验中

实验沿用原项目 LWT 分支的预订模型，在独立表 `lab_reservations_by_hotel_date` 上使用 `INSERT ... IF NOT EXISTS` 竞争相同酒店、入住日与房号，观察 `[applied]`。条件更新和删除使用 `UPDATE/DELETE ... IF EXISTS`，分别验证记录存在和不存在时的行为。代码和原项目的对应关系见 [条件语句示例](06-conditional-writes.md)。

当前预订业务需要维护两张表。Cassandra 的条件 BATCH 不能跨表或跨分区，所以不能简单给现有 BATCH 增加 `IF NOT EXISTS`，就声称实现了两表原子并发控制。[Cassandra 5.0.9 条件 BATCH 校验](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/cql3/statements/BatchStatement.java)

同样，预订一个房间的多个住宿日，会涉及多个日历位置。单个主键上的 LWT 成功，并不自动意味着整个日期区间都已可靠占用。

## 删除、TTL 与磁盘空间

DELETE 和 TTL 到期后，查询结果会反映删除，但磁盘文件中的旧数据不是立即全部移除。Cassandra 后续通过 compaction 等机制处理过期或删除的数据。

主业务没有 TTL，避免预订无提示过期。独立 ttl 实验使用单独的表演示过期，不影响 API 的数据。

## 下一步可以怎样扩展

先写下业务需要保证的行为，再选择机制。例如，是否允许重复请求、能否接受查询表短暂落后、如何恢复未完成的投影、冲突时返回什么。不要先选一个更复杂的事务或消息组件，再反过来假设它解决了所有一致性问题。
